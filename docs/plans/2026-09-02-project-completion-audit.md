# 林元元商城全项目收尾实施计划

> 日期：2026-09-02
> 范围：A 端消费者小程序、B 端运营后台、C 端分销员分包、CloudBase 云函数与数据迁移。

## 目标

在保留现有数据和未提交改动的前提下，补齐上线前仍有风险的交易、资金、配置和验收环节；所有本地可完成事项由代码和自动化测试完成，真实云环境部署、真实支付/退款/提现只保留最少的人工验收步骤。

## 当前结论

- A/B/C 三端结构和主要业务页面已经存在，权限隔离、库存锁定、支付回调、佣金、退款、后台扫码登录均已实现。
- 自动化基线已经覆盖主链路，但支付未配置时会自动模拟成功，这是上线阻断风险。
- 提现申请和审核包含“先查后写”的并发窗口，需要事务化和幂等键。
- 初始化脚本仍创建旧集合 `carts`，运行时实际使用 `cart`；后台部分文案仍混用“代理”。
- 物流已支持发货信息和轨迹展示，但外部物流查询尚无服务商接口；本轮先完善可验证的状态/轨迹数据契约，不伪造第三方查询能力。

## 实施任务

### 1. 支付安全收口

- 修改 `cloudfunctions/pay/index.js`：缺少商户号或支付配置时明确失败，不再隐式模拟付款。
- 模拟支付改为“双开关”：数据库明确开启，且云函数环境变量明确允许；默认永远关闭。
- 已支付订单返回真实的幂等状态，不再谎报 `mock: true`。
- 修改初始化和迁移默认值，确保新环境不会生成可直接模拟付款的配置。
- 增加 smoke/E2E 回归断言。

### 2. 提现并发与资金幂等

- 提现申请使用事务重新计算已结算佣金和审核中金额，再写入申请。
- 支持客户端请求幂等键，避免重复点击生成两笔申请。
- 后台审核使用事务锁定申请状态，并在同一事务内消费佣金、生成资金流水。
- 保留人工线下打款语义，后台明确展示“确认已打款”，不宣称已调用自动转账。
- 增加重复申请、重复审核、余额变化和负余额测试。

### 3. 售后与退款一致性

- 退款记录增加固定退款单号和处理阶段，重复操作复用同一幂等键。
- 无真实交易号时不得把退款描述成线上退款成功，保持“待线下退款确认”的明确状态。
- 未发货退款自动回库；退货退款必须确认收货后才允许选择回库。
- 检查资金流水、库存调整和佣金冲销唯一键。

### 4. 配置、术语与数据契约清理

- 初始化脚本统一使用 `cart` 集合，并将支付默认配置改为安全值。
- B/C 端统一“分销员”术语，清除可见的“代理”旧文案。
- 补充支付、物流和提现的上线状态说明，让后台能直接看出哪些能力尚需真实资质。
- 更新部署文档和上线前清单。

### 5. 自动化与界面验收

- 运行 `npm run smoke`、`node scripts/e2e-mock.js`、`npm run lint:functions`。
- 检查小程序页面清单、分包路由和云函数语法。
- 用浏览器验证 B 端登录态、总览、订单、财务、提现、设置页面。
- 用微信开发者工具验证 A 端入口和 C 端未激活隔离。
- 输出仅需用户执行的最终清单：云函数上传部署、真实小额支付、退款和人工打款验收。

## 完成标准

- 未显式允许模拟支付时，任何订单都不能被模拟标记为已支付。
- 同一提现请求和同一审核请求重复执行只产生一次状态变化与一次资金流水。
- 清理、库存、支付、退款、佣金和权限测试全部通过。
- 后台可见文案与实际能力一致，不把“人工确认”描述为“自动打款”。
- 本地代码达到可部署状态，剩余操作只涉及用户持有的微信/CloudBase/商户权限。
