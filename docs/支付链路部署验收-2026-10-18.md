## 3. 提现验收：新交易、新提现

1. 准备不同微信的消费者与 active 分销员，通过正常推广、支付、收货产生已结算佣金，记录各端初始金额。不能通过改余额伪造正常链路。
2. 分销员申请预算内的新小额提现。提现页和分销看板可用额同步减少申请金额，处理中增加，累计已提现及财务现金支出不增加；重复提交同一请求不新增申请。
3. 店主/财务审批。新单应为 `accountingVersion=2`，关联佣金 `withdrawing`，可用额不再次减少，列表显示“提现处理中”。未确认渠道成功前不得为 `paid` 或新增 posted 佣金支出。
4. 若接口失败，收集脱敏 code/HTTP状态/阶段；保留原单号及占用。查询错误、超时或未知结果立即停止再提交，先由有权限的人核对原单。只有明确失败/关闭/不存在才允许新尝试；不要拿旧 ¥1 单测试配置。
5. 微信返回待本人确认时，由分销员本人点击“确认收款”。取消后可再次领取；非本人不能领取参数。缺确认凭证时先查原单，不制造参数或换号。
6. 本人完成后，由授权操作员或本人入口核对原单。只有渠道 `SUCCESS` 才将关联佣金标为 `paid`、写入一笔 posted 支出、更新提现成功。重复查询/重复点击不能新增出款或流水。
7. 同时核对提现页、分销看板、佣金列表、经营收支：可用、处理中、累计佣金、累计已提现、负债和现金支出应一致。若客户端打开确认页成功但渠道未成功，保持处理中。

参考：起始可结算佣金 500 分、申请 100 分；审核和待确认时可用 400、处理中 100、累计已提现增量和现金支出增量均为 0；最终成功后可用仍 400、处理中 0，累计已提现与支出增量均为 100。实际商品价格/佣金率及预算另由执行方选择，不要求按此例充值或付款。

## 4. 退款验收：另一笔新订单

1. 独立准备实际支付订单，记录订单、SKU库存、佣金和财务初始值。分别覆盖仅退款与退货退款；退货退款先确认实际收货。
2. 消费者申请后，店主/财务同意。允许立即提交一次退款，但接口仅受理时，订单仍售后中、退款为渠道处理中，库存/佣金/现金支出不能提前完成。
3. 使用 B 端已有“处理并核对退款”入口，由有权限的微信扫码处理；或使用已有审批/重试入口按原单核对。只读查询退款页面始终只读，不承担自动入账。
4. 最终查询为对应原商户、原退款号、原订单和金额的 `SUCCESS` 后，才一次性完成退款、订单、库存、佣金冲销及退款支出。直连响应必须通过签名/商户验证；缺查询证书不应阻止纯查询，但实际直连退款仍需证书。
5. 已提交后遇到超时、UNKNOWN、查询 NOT_FOUND 或自触发响应丢失，不切通道、不更换退款号、不再次出款，继续查原单或人工核查。仅明确 `NOTENOUGH` 拒绝时，操作员确认余额并查单后可按原号原通道重试，后台核对 worker 不自动重试资金。
6. 重复核对不重复返库存、冲佣金或记支出；退款完成后再拒绝不得反转结果。另验一笔“佣金已提现/正被提现占用后发生退款”，核对各端余额及一次负向冲销，不能重复释放额度。

## 6. 停止与恢复

金额/身份/签名/单号不符、资金结果未知、重复请求迹象或数据库事务失败时，停止该资金场景，保存原号，核对渠道后再决定。不得仅靠点重试判断是否修好。

本轮没有改历史资金记录。若新版本已写入 `withdrawing` 等状态，不直接退回只认识旧状态的整包；先暂停新申请，由负责人备份、核对在途单和账本，选择兼容版本或单独恢复方案。代码基线可定位，但回退代码不能撤销外部已发生的资金结果。
