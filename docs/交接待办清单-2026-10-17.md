### 5.4 为什么没有直接点“查询到账”

修复前 `queryWithdrawalTransfer` 会回写状态、失败/关闭时清空当前单号。本轮修复后仍通过共享处理器回写状态及成功账本，但失败保留原号，明确终态重试时才归档并更换；它依然不是纯只读接口。本轮没有对真实旧单调用此接口。

`wxpay-transfer.js` 的 `queryBill` 是独立的微信 GET 查单逻辑，但本机执行需要受控商户签名条件；本次没有私钥，也没有已验证的商户平台会话，所以只完成数据库核对，没有完成微信原单查账。后续渠道查询应保留原单号并明确是否会回写业务数据。

## 6. 私钥与“用现在账号测试”的关系

### 6.1 私钥是什么，在哪里用

这里的私钥是微信支付商户 API 的请求签名私钥，用于给查单、转账请求签名。它不是微信密码，不是小程序 AppSecret，也不是 CloudBase 自定义登录私钥。

提现模块实际读取路径为 `cloudfunctions/admin/certs/apiclient_key.pem`。原交接已说明密钥和备份不随 Git，需单独受控交接。本机检查未发现该私钥、配套证书或 `backups/`；这不证明云端部署包缺失，也不是已经查明的提现故障原因。

### 6.2 不同验证方式的区别

| 方式 | 谁使用商户私钥 | 当前能否进行 |
| --- | --- | --- |
| 本地模拟 E2E | 不使用真实商户私钥，云接口被 mock 替换 | 可以做代码分析和模拟验证，不证明真实到账 |
| 本机直接向微信查账/转账 | 本机请求程序使用私钥及匹配的商户信息 | 本机签名条件未交接，不具备已验证的真实接口调用条件 |
| 当前微信通过小程序/B 端走已有流程 | 已部署的云函数使用云端凭据；用户微信是业务身份 | 不要求先把私钥拿到本机，但业务身份、云端凭据、商户权限和出口 IP 均需核对，整条链路尚未实测 |
| 改为另一个支付商户 | 新商户需要自己的配置与凭据 | 用户尚未明确提出更换商户，不能把换微信账号当作换商户 |

因此，可以围绕当前微信和已有云环境准备复现；拿到本机私钥不是所有页面测试的前提，但也不能承诺当前账号已经能打款。

### 6.3 希望复现的业务路径

分销员申请提现 → 店主/财务审批 → 云函数向已配置商户发起转账 → 分销员本人确认收款 → 核对渠道结果 → 核对提现、佣金与财务报表。

使用当前账号的前置条件：合适的分销员身份及佣金、具备审批权限的测试人员、可用的小程序版本、完整的云端配置，以及真实资金测试安排。单有开发者工具登录或 CloudBase 权限不够。

原商户联系不上是当前交接难点，不等同于云端凭据已失效，也不代表现在有权或有能力改原商户设置。尚未确认是否有其他现有管理员可以配合。若进行新流程验收，应单独准备测试记录；历史 ¥1 单先保留，不能用它反复重试来判断配置是否修好。
